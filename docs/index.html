01

What it does

Two independent capabilities live in one service. They share a database, a config layer, and an account system — but the event pipeline and the Kaspi integration never touch each other.

◇ Event analytics

A minimal event sink. Post single events or batches of up to 1,000; every event is a row with a name, an optional user identity, a timestamp, and free-form JSON properties. Three read endpoints aggregate them: volume over time, top events, and unique-user counts — each filterable by time window and event name.

◈ Kaspi seller sync

Register a Kaspi.kz merchant with just an email + password. The backend logs in headlessly (SSO → OAuth2), derives the merchant UID, and pulls the entire product catalog into Postgres. It re-syncs hourly, auto-refreshes expired sessions, soft-archives vanished SKUs, and lets you attach a private cost price (COGS) to each product.

⚠

Auth coverage is uneven — by design or gap?

The /kaspi/* routes require a JWT. The /events and /reports routes currently have no guard — anyone can ingest events and read every report without a token. That's fine for public ingestion behind a write-key, but open reports may be unintended. Flagged during the 2026-07-08 review.

04

Authentication

Accounts are our own analytics accounts — one account owns one or more Kaspi sellers. Register or log in, then send the returned token as a bearer header on Kaspi routes.

🔑 The token

A 7-day HS256 JWT signed with JWT_SECRET. Payload is { sub: userId, email }. Passport's JWT strategy validates it and attaches { userId, email } to the request, read via the @CurrentUser() decorator.

🛡 Ownership

Every Kaspi route resolves the seller and checks seller.userId === user.userId, returning 403 otherwise. One user can never see or sync another user's sellers or products.

Send the token

Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9…

◆

The archive rule

When a SKU disappears from a sync, its row isn't deleted — archivedAt is stamped and the listing hides it, preserving its costPrice. If the SKU returns, the upsert clears archivedAt and it reactivates. The catalog is never nuked from a flaky zero-offer response.

07

Security & secrets

Two distinct crypto schemes for two distinct jobs, both in crypto.util.ts.

# Passwords

App-user passwords are one-way scrypt hashes with a per-password 16-byte salt, stored as scrypt$salt$hash. Verification uses timingSafeEqual. Never reversible.

⚿ Kaspi secrets

Cookies, tokens, login & password are AES-256-GCM encrypted at rest (gcm$iv$tag$cipher) under CREDENTIALS_ENC_KEY. A dedicated sellerView projection guarantees ciphertext never leaves the service.

✓ SQL safety

Drizzle parameterizes everything. The one raw fragment — date_trunc's interval — is checked against an INTERVALS allowlist before it reaches SQL, so no user value is ever interpolated.

Scheduled work

KaspiScheduler registers one cron via @nestjs/schedule: EVERY_HOUR → syncAllDue(), which re-syncs every seller that has either a stored cookie or stored credentials. Sellers flagged needs_reauth self-heal on the next run if their credentials still work.
